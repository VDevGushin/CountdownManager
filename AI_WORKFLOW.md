# Работа над проектом с ИИ

## Роли

Владелец проекта выступает менеджером продукта: формулирует проблему, желаемое поведение, приоритет и ограничения. Писать код, выбирать Swift API или составлять техническое задание ему не требуется.

ИИ выступает ответственным разработчиком и самостоятельно:

1. Изучает текущий код и воспроизводит проблему.
2. Предлагает решение на уровне продукта, если есть заметные компромиссы.
3. Выбирает архитектуру и реализует изменение.
4. Добавляет или обновляет проверки.
5. Собирает приложение и проверяет затронутые сценарии.
6. Обновляет README, `AGENTS.md` и `VERIFICATION.md`, когда меняется поведение или процесс сопровождения.
7. Чётко сообщает, что готово, что проверено и какие ограничения остались.

## Как ставить задачи

Достаточно написать обычным языком, например:

- «Хочу уведомление за неделю и за день до события».
- «После добавления события приложение зависло».
- «Сделай интерфейс компактнее».

ИИ должен сам превратить такой запрос в техническую работу. Уточняющий вопрос нужен только тогда, когда ответ действительно изменит продуктовый результат.

## Обязательные правила разработки

- Не изменять и не удалять пользовательский `countdowns.json` во время тестов.
- Не записывать названия событий, заметки и emoji в диагностический журнал.
- Не выполнять файловые операции хранилища на главном UI-потоке.
- Сохранять совместимость с macOS 13+, если отдельно не согласовано иное.
- Не добавлять сторонние зависимости без явной пользы и объяснения.
- Не считать ручную проверку заменой автоматическим тестам для логики ядра.
- Перед установкой проверять сборку и подпись; установленную рабочую версию сохранять до завершения проверки новой.
- Перед каждым коммитом проводить отдельное self-review всего подготовленного diff: проверить границы изменения, корректность, крайние случаи, обработку ошибок, асинхронность, совместимость данных, приватность, доступность и поддержку macOS 13+ там, где это применимо.
- До коммита запускать `git diff --cached --check`, релевантные автоматические проверки и сборку. Все найденные замечания исправлять, после чего повторно просматривать обновлённый diff.
- Не утверждать, что код проверен, если какая-либо релевантная проверка не выполнялась; оставшийся пробел проверки указывать явно.
- После реализации дополнять unit-тесты для логики и UI-тесты для пользовательских состояний и действий, которые можно надёжно автоматизировать.
- Обязательная последовательность для завершённой задачи: написать тесты → прогнать unit/UI-наборы → провести self-review всего diff → исправить замечания → повторно прогнать те же тесты → только после зелёного повторного прогона создавать коммит и, при запросе владельца, выполнять push.
- Если системный UI-сценарий нельзя автоматизировать в доступной среде, добавить ближайший детерминированный smoke/state-тест, явно описать ограничение и при возможности выполнить ручную проверку. Не называть такую проверку полным end-to-end покрытием.
- На одну задачу допускается не более пяти полных циклов исправления и проверки. Если после пятого цикла тесты или ревью всё ещё не дают зелёный результат, ИИ останавливается без commit/push и обращается к менеджеру продукта: показывает конкретный блокер, собранные данные и возможные варианты решения.
- Менеджер продукта может явно разрешить дополнительные итерации. Стабилизацию новой тестовой инфраструктуры до получения первой надёжной зелёной базы можно продолжать без ограничения числа попыток, но нельзя ради этого ослаблять поведение продукта или удалять корректные проверки.

## Definition of Done

Задача завершена, когда:

- пользовательский сценарий реализован;
- ошибки обрабатываются без потери данных;
- релевантные CoreChecks проходят;
- релевантные UI-проверки проходят;
- приложение успешно собирается;
- интерфейс проверен для пользовательских изменений;
- документация соответствует фактическому поведению;
- полный подготовленный diff прошёл self-review, а нерешённых замечаний не осталось;
- после self-review повторно прошли те же unit/UI-проверки;
- при запросе на установку или публикацию проверен именно установленный или опубликованный результат.

## Выпуск версии

Для локальной установки релиза ИИ обновляет версию в `Resources/Info.plist`, собирает `.app`, проверяет подпись, сохраняет предыдущую установленную копию, устанавливает новую и проверяет запуск на существующих данных. Публикация GitHub Release — отдельное внешнее действие и выполняется только по запросу владельца.

Фраза владельца **«Собираем публичный релиз для пользователей»** считается явным разрешением подготовить и опубликовать GitHub Release. Если версия не указана, повышается patch-версия. ИИ проходит полный test/review gate, собирает и проверяет приложение, создаёт ZIP-архив, публикует релиз, прикладывает архив и проверяет опубликованный файл. Установка новой версии в `/Applications` в эту команду не входит без отдельной просьбы.
