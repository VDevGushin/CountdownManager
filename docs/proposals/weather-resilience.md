## Подтверждённое поведение и эпизод 19 октября

В доступном локальном `countdown.log` прочитаны следующие записи. Время переведено
из UTC в МСК; журнал использован только для чтения. Содержимое событий не читалось.

| Время МСК | Наблюдение |
| --- | --- |
| 10:56:24 | Запуск 1.11.0 build 20, ручное местоположение, после загрузки demanded=3; старт трёх источников |
| 10:56:25 | MET: HTTP 200, decode=ok, days=10, full_days=1, usable_days=1; затем cache=expired, fresh_for_s=0, retry_in_s=1800 |
| 10:56:37 и 10:56:40 | wttr и Open-Meteo: URL timeout; каждому назначено 300 секунд |
| 11:01:39 | wttr завершился успешно; публикация demanded=3, usable=1 |
| 11:01:41 | Open-Meteo завершился успешно; публикация demanded=3, usable=3 |

`usable_days` в транспортном журнале описывает весь пакет, а не конкретные события.
Из одного usable дня MET нельзя заключить, что это было именно сегодня. Снимки
пользователя и подтверждение появления погоды переданы оркестратором; самостоятельной
проверки этих снимков в этом разборе нет.

В `Weather.swift:459–481` успешному ответу назначаются `freshUntil=Expires` либо
полчаса при отсутствии распознанного Expires и
`nextRequest=max(receivedAt+1800, freshUntil)`. Прошедший Expires допустим для
`validDate`: проверяется конечность числа, а не будущее. Публикация берёт только
`freshUntil>now`. Поэтому код допускает и объясняет состояние «200, пакет есть,
использовать нельзя, повтор через полчаса». Это подтверждённая механика и проблема
доступности; она соответствует нынешнему PRODUCT, а не нарушает его.

`WeatherTransport.swift` читает Expires, Last-Modified и Retry-After, но не Date,
Age, Cache-Control и ETag. Текущее 304 без Expires получает новые 1800 секунд;
старый Expires при этом заменяется nil. Без полного набора метаданных такая
реализация не может корректно учитывать все ограничения HTTP-кэширования.

Причина немедленной просрочки конкретного MET-ответа **не установлена**. Прошедший
Expires — наиболее прямой путь в прочитанном коде; скачок часов между транспортом
и контроллером тоже нужно исключить. Журнал не содержит соответствующих заголовков.
Нельзя приписывать происшествие CDN, сервису, VPN или системным часам без новых данных.

## Сохраняемые границы

- Один пакет каждого источника на область, зону и диапазон из 16 дат. События на
  одну дату не умножают запросы. Максимум четыре контекста в памяти.
- UI получает только полный день с температурой и категорией. Сохраняются медиана,
  голосование и фактические периоды; текущая температура и оставшиеся часы не
  заменяют максимум за день. Успешный MET утром может закономерно не покрывать сегодня.
- OFF, смена местоположения, удаление последнего спроса и shutdown отменяют работу.
  Generation, computation revision и проверка текущего спроса действуют также для
  повторов, восстановления с диска и поздних callbacks.
- События, их JSON, предпочтения пользователя и системные разрешения не используются
  как fixtures. Никаких новых ключей, аккаунтов, серверов или источников.
- Логирование остаётся ограниченной асинхронной записью без ожидания диска на UI actor.

## Владельцы состояния и минимум новых сущностей

`WeatherController` остаётся единственным владельцем спроса, контекстов, поколений,
публикации и одного scheduler. `WeatherTransport` отвечает за запрос и типизированные
метаданные ответа; адаптеры — за нормализацию. Consensus остаётся вне UI actor.

Достаточно двух новых небольших типов значений: `WeatherHTTPMetadata` и чистой
`WeatherRequestPolicy`. Первый переносит разобранные метаданные, validator и времена
приёма; второй вычисляет допустимость использования и следующий срок запроса.
Новый сервисный слой, отдельный actor на источник и UI view model не нужны.
При одобрении диска добавится один `WeatherDiskCache` с сериализованным фоновым I/O.

Существующий SourceCache расширяется данными о представлении и попытках. У этих
данных разные сроки жизни: свежесть пакета, валидатор, число последовательных
временных сбоев, использованные быстрые попытки и срок следующего обращения.
Cooldown по Retry-After и общий бюджет источника хранятся отдельно от четырёх
вытесняемых контекстов, но у того же контроллера: смена города или OFF/ON не должны
обходить ограничение сервера. Эти небольшие записи ограничены тремя источниками.

Не вводить одно линейное enum-состояние, объединяющее наличие данных и сеть.
Источник может одновременно иметь свежий пакет и выполняющийся refresh.

| Ось | Состояния и переходы |
| --- | --- |
| Представление | absent → fresh при пригодном 200; fresh → expired по сроку; expired → fresh после корректной валидации; incomplete остаётся внутренним результатом |
| Работа | idle → inFlight только при спросе и разрешённом сроке; исход → waiting либо idle; offline приостанавливает сетевые попытки |
| Поколение | OFF/location/empty/shutdown меняют generation, отменяют сеть, scheduler и вычисление; поздний исход ничего не меняет |

Сохранить один parent task со structured task group. Scheduler не открывает второй
batch, пока группа не завершилась; просроченные задачи пересматриваются при её
завершении. Быстрый повтор иногда задержится до завершения соседа, ограниченного
ресурсным timeout в 20 секунд. Это разумнее нового механизма независимых task owners
для выигрыша нескольких секунд. Зависший некооперативный fake нужен в проверке
отмены, но не должен блокировать будущее поколение контроллера.

## Предлагаемая политика запросов

Интервалы ниже — инженерные начальные значения, не требования сервисов и не обещание
доступности. Jitter выбирается один раз при назначении срока, с внедряемым генератором
в тестах. Все интервалы отсчитываются после исхода предыдущей попытки.

Быстрый режим допустим только при временной ошибке, если есть непокрытые нужные даты,
которые источник способен покрыть по своему горизонту, и нет ещё свежего пакета этого
источника с уже известным отсутствием покрытия. Для начального unknown coverage
допускается одна ограниченная серия. Частичный успешный ответ сам по себе не сбой.

| Исход или условие | Следующее обращение | Обоснование |
| --- | --- | --- |
| Первый запрос, есть спрос и область | Сразу, три источника параллельно | Сохранить ранний первый результат |
| Timeout, connection lost, временный DNS/connect error; быстрый режим | После первого сбоя 10–20 с, после второго 45–75 с; максимум два быстрых повтора | Пережить короткий сбой после запуска без пяти минут пустоты |
| Дальнейший временный сбой или быстрый режим не нужен | 300–360 с, затем 900–1080 с, затем 1800–2160 с | Сократить постоянный трафик; верхняя ступень повторяется |
| 429 или 503 | Без быстрых повторов; минимум 300–360 с и не раньше Retry-After, далее обычный backoff | Не усиливать перегрузку |
| Другие временные 5xx, HTTP 408 | Ограниченная быстрая серия допустима при нехватке данных, затем backoff | Повторяемый идемпотентный GET |
| 200/304 с нулевой свежестью | Один повтор через 60–90 с; повторное такое состояние → 300–360 / 900–1080 / 1800–2160 с | Дать серверному кэшу обновиться, исключить revalidation loop |
| Успех с короткой положительной свежестью | После истечения срока, с jitter 0–15 с и минимумом 60 с от предыдущего завершения | Исключить полчаса обязательной пустоты; до expiry данные доступны |
| Успех без HTTP freshness | Сохранить явную локальную эвристику 1800 с; refresh после неё | Совместимость с текущими источниками; это эвристика, не гарантия сервера |
| Свежесть ≥1800 с | По серверному сроку, без раннего запроса | Не скачивать ещё действующее представление |
| Декодирование, неверные units/schema, обычные 4xx, TLS trust error | Без быстрой серии; следующая обычная проверка через 1800–2160 с, либо после изменения контекста | Быстрый GET не исправляет схему, сертификат или постоянный отказ |
| Cancellation | Ни ошибки, ни нового повтора | Уважение жизненного цикла |

Для 200alreadyExpired и короткого TTL меняется нынешняя 30-минутная нижняя граница.
Требование не показывать просроченное остаётся. Freshness и серверный запрет запросов
никогда не смешиваются: `nextAttempt=max(policyDeadline, serverNotBefore,
providerCooldown, budgetDeadline)`. Более поздний серверный срок не обрезается
клиентским cap. Нижний ограничитель 60 секунд не разрешает запрос раньше expiry.

На источник — максимум шесть стартов за скользящие десять минут суммарно для всех
городов; максимум три одновременных запроса, один на источник. Превышение бюджета
откладывает запрос до освобождения самого раннего слота. Смена даты/контекста не
обнуляет бюджет. Быстрая серия не возобновляется от перестановки событий, refresh,
открытия панели или OFF/ON. Сброс серии допускается после пригодного успеха либо
30 минут без стартов этого источника. Признак использования серии переживает
вытеснение контекста в пределах текущего процесса.

Свежий успешный источник не перезапрашивается из-за чужого сбоя. При позднем успехе
пересчитывается только актуальный спрос; существующий badge не ждёт остальных.
Счётчик временных ошибок сбрасывается после свежего валидного ответа, а цепочка
alreadyExpired — только после ответа с положительным сроком. Успех без покрытия
дня не запускает быстрый цикл для получения невозможных прошедших часов.

На constrained/expensive path или в режиме экономии энергии быстрые серии отключены;
обычные запросы разрешены. При явно unsatisfied path не выполнять запланированные
GET, но продолжать истечение свежести. На восстановление — debounce 2–5 с, один
совмещённый refresh; он не обходит Retry-After и бюджет. После длительного offline
можно снять только обычный backoff соединения один раз, без нового быстрого бюджета.
Изменения path не означают доступность конкретного сервиса через рабочий VPN.

Один NWPathMonitor включается только при ON и спросе, событие доставляется контроллеру.
При unknown path первый GET разрешён. Его назначение — подавлять заведомо лишние
повторы, не заменять реальный результат URLSession. Не добавлять ping/HEAD проверки.
Сохраняются текущие request timeout 15 с (wttr 12 с) и resource timeout 20 с;
`waitsForConnectivity=false` задаётся явно, чтобы ожиданием управлял один scheduler.
Уменьшение всех timeout повысило бы число ложных ошибок на медленной сети.

## HTTP freshness и часы

Нормативная опора: [RFC 9111, freshness и age](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)
и [обновление после 304](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4).
`max-age` приоритетнее Expires; возраст учитывает Date, Age и длительность запроса.
Last-Modified является validator, а не временем годности.

Чистый расчёт получает wall-clock при старте/приёме и монотонную длительность:

```text
lifetime = max-age, иначе max(0, Expires - Date)
apparentAge = max(0, responseWall - Date)
initialAge = max(apparentAge, Age + requestDuration)
remaining = max(0, lifetime - initialAge)
```

После приёма возраст увеличивается по ContinuousClock. При отсутствующем Date и
наличии Expires — консервативно `max(0, Expires-responseWall)`; без обоих и без
max-age — помеченная локальная эвристика 1800 с. Некорректные/конфликтующие директивы
не дают эвристического продления. `no-cache` требует валидации перед повторным
использованием; `no-store` исключает сохранение пакета. В предложенной реализации
такие ответы не питают длительно живущий badge. `must-revalidate` не разрешает stale.

При наличии max-age и отсутствии Date считать apparentAge равным нулю и учитывать
Age и длительность запроса; отсутствующий Age равен нулю. Если нет явной freshness,
но есть Age, вычитать известный возраст из локального эвристического бюджета.

304 применяется только к существующему представлению того же запроса и подходящему
validator; новые поля заменяют одноимённые старые, отсутствующие сохраняются.
Возраст пересчитывается по метаданным валидации. Отсутствующий Expires сам по себе
не даёт новых 30 минут. Неподтверждённая свежесть → bounded revalidation; 304 без
локального тела → один unconditional GET на очередном разрешённом слоте.

Двухчасовое расхождение локальных часов нельзя автоматически «исправить» по одному
Date: оно неотличимо от старого ответа без дополнительных свидетельств. При смене
wall-clock относительно ContinuousClock более чем на 60 с считать свежесть спорной,
скрыть затронутые значения и назначить ограниченную проверку. Backoff и delta
Retry-After сохраняются по монотонным срокам, даже если часы перевели назад.
Date/Expires с истёкшим сроком не превращаются в receipt+1800. Для абсолютного
Retry-After использовать консервативный максимум локальной разницы и разницы с
серверным Date, если тот валиден. Это может задержать восстановление при неверных
часах, зато не создаёт преждевременные обращения.

Значения срока на диске не являются монотонными: после запуска проверяются wall-clock
и сохранённые времена; подозрительное будущее или откат часов запрещают публикацию
до проверки. Монотонный instant между процессами не сериализуется.

Для HTTP-date нужен разбор форматов получателя из RFC 9110, а не только нынешний
IMF-fixdate. Retry-After в секундах — неотрицательное целое с защитой от overflow;
дроби/NaN не принимаются. Прошедший Retry-After не требует мгновенного повтора.
[RFC 9110, Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

## Проверка неопределённостей платформы и сервисов

Вопрос: нужен ли ещё один timeout или URLCache для устойчивости? Apple различает
[ожидание данных](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/timeoutintervalforrequest)
и [общий ресурсный срок](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/timeoutintervalforresource).
[waitsForConnectivity](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/waitsforconnectivity)
относится к установлению соединения; восстановление разорванного запроса всё равно
принадлежит вызывающему коду. Следствие: оставить ограниченный ephemeral transport,
управлять повтором в контроллере. Новый URLCache создал бы второго владельца кэша.

[ContinuousClock](https://developer.apple.com/documentation/swift/clock/continuous)
продолжает ход во время сна. После wake нужно один раз пересчитать сроки, день и
спрос, без воспроизведения всех пропущенных повторов. Нужен явный мост wake/clock/zone
в существующую refresh-границу; точный порядок системных уведомлений предстоит
проверить на поддерживаемом macOS. Минимальный будущий probe: изолированная копия,
один цикл sleep/wake, записи монотонного и wall времени, проверка отсутствия burst.
В этой документальной задаче такой эксперимент не выполнялся.

[NWPathMonitor](https://developer.apple.com/documentation/network/nwpathmonitor)
наблюдает изменения сети; [NWPath](https://developer.apple.com/documentation/network/nwpath)
сообщает expensive/constrained. Это основание для подавления лишних попыток,
а не доказательство успешного HTTPS к конкретному хосту.

[MET Getting Started](https://api.met.no/doc/GettingStarted) и
[Terms of Service](https://api.met.no/doc/TermsOfService) требуют учитывать Expires,
использовать If-Modified-Since, избегать ненужного трафика и синхронных всплесков.
Фиксированного обязательного минимума 30 минут там не установлено. Поэтому
короткий bounded повтор после уже истёкшего ответа — предлагаемая политика клиента,
а не утверждение о гарантированном обновлении MET через минуту. User-Agent сохраняется.

[Open-Meteo](https://open-meteo.com/en/pricing) ограничивает бесплатный некоммерческий
доступ и не даёт ему uptime guarantee. Предложенный локальный бюджет не гарантирует
общую квоту при общем IP/VPN. [wttr upstream](https://github.com/chubin/wttr.in)
описывает JSON, но не подтверждает SLA и отдельные лимиты хоста wttr.is; для него
применяется консервативная клиентская политика и фактические HTTP-ответы.
Живой HTTP-пробой при этой работе не выполнялся: документация не доказывает текущую
доступность трёх сервисов с данного Mac.

## Ограниченный дисковый кэш как отдельный этап

Предпочтительный первый вариант после отдельного одобрения: сохранять только ручные
города. AUTO остаётся только в памяти. Сохранение AUTO даже с хешем округлённых
координат меняет privacy-контракт: область можно восстановить перебором, хеш не
является анонимизацией. Для повторного использования AUTO после запуска всё равно
нужно свежее разрешённое получение координат; старое место не подменяет текущее.

Один версионированный файл в пользовательском Caches, вне event JSON, preferences
и диагностического архива. Схема содержит schemaVersion, normalizationVersion,
request variant, source, rounded area или manual city ID, IANA zone, диапазон дат,
фактические UTC-границы каждого дня, нормализованные samples, полученные HTTP
метаданные, fetched/validatedAt и срок. ETag/Last-Modified связаны с точным запросом.
Ключ включает область+зону+startDay+dayCount+source+variant; event UUID/названия
не входят. Для MET, URL которого не включает диапазон, нормализованный пакет всё
равно нельзя переносить между диапазонами без проверки покрытия.

Сохраняются только проверенные полные samples с температурой и категорией, без raw
body. Не записывать no-store/no-cache, неясную свежесть и данные с нулевым остатком.
TTL не перезапускается при чтении: доступно лишь до исходного freshUntil, дополнительно
не дольше шести часов с последней успешной валидации. Шесть часов — предел хранения,
а не разрешение продлить прогноз. Для 304 нужен полный пригодный сохранённый пакет
с точной идентичностью; иначе unconditional GET. Retry-After/cooldown сохраняется
в небольшом техническом разделе только при одобрении диска, чтобы relaunch не
обнулял запрет сервера; неопределённые часы обрабатываются консервативно.

Максимум четыре контекста, три источника, 16 дней: 192 samples. Файл не более
256 KiB; проверка размера до декодирования, количества/диапазонов/units после.
Удалять expired и LRU, отбрасывать несовместимую schema/normalizationVersion,
повреждённый файл, symlink и неверные ключи. Никакой попытки «исправить» event data.
Сбой записи/чтения оставляет обычный сетевой путь работоспособным.

Чтение начинается асинхронно вместе с сетью, не до показа интерфейса. Контроллер
принимает результат только для актуального generation/query/demand. Сравнение версии
записи не позволяет запоздалому диску заменить новый сетевой ответ. Запись объединяет
серийные исходы в один snapshot, выполняется сериализованно в фоне через временный
файл и атомарную замену. На OFF/invalidation действует fence: старый writer не
может восстановить удалённый кэш после очистки. Никакого синхронного flush при выходе.

При смене города выбран только соответствующий ключ; старые города можно удерживать
в пределах LRU. OFF немедленно прекращает чтение/публикацию и очищает погодный файл
асинхронно с fence. Удаление последнего события делает то же. При midnight меняется
range key, прошлые сутки не переименовываются; первая версия сознательно не переносит
вчерашний пакет на новый диапазон. При смене зоны/DST сверяются и IANA zone, и UTC
интервалы, а несовпадение запрещает reuse. Caches может удалить сама ОС — отсутствие
файла штатно. Это локальный чувствительный кэш, не зашифрованное хранилище секретов;
нужны доступ только пользователю, исключение из backup и отсутствие в экспорте.

Просроченные данные **не показывать**. Отдельный stale fallback потребовал бы нового
продуктового решения о допустимом возрасте и обозначении давности в UI; текущий plain
badge этого не объясняет. Поэтому stale режим в предпочтительный вариант не входит.

## Диагностика для установления причины

В исходы добавить только ограниченные числовые/enum-поля: наличие и parse-result
Date/Age/Expires/Cache-Control, age_seconds, expires_minus_date_seconds,
expires_minus_receipt_seconds, freshness_reason, remaining_seconds, retry_reason,
attempt_index и выбранный delay. Отрицательные относительные сроки должны оставаться
отрицательными в диагностике, а не превращаться в ноль, как нынешний formatter.
Сырые headers, validator, URL, координаты, город и body не писать. Диапазоны чисел
ограничить; ошибки разбора фиксировать категорией. Никакого дополнительного HTTP,
ожидания очереди или диска при формировании снимка. Это позволит разделить истёкший
Expires, влияние Age, приоритет max-age и скачок часов при следующем эпизоде.

## Детерминированная regression матрица

Расширять существующие `WeatherConsensusChecks` и `WeatherDiagnosticsChecks`, а не
дублировать стенд. Инъекции: wall и monotonic clocks, scheduler, фиксированный jitter,
URLProtocol/ответы источников, network/energy events, временная директория кэша.
Тесты не ждут реальное время, не обращаются в сеть и не читают production data.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Холодный запуск, три timeout | При jitter=0 первый повтор ровно +10 с, второй +45 с, затем +300/+900/+1800; не более двух быстрых повторов |
| Дубли событий, повторные refresh, burst demand | Один запрос на источник/range; бюджет не сбрасывается; число событий не влияет на сеть |
| Один ранний и два поздних успеха | Публикация после первого; последовательный consensus 1/2/3; новая схема не ждёт всех |
| Успех partial day, отсутствующий максимум/категория, горизонт меньше спроса | Неполная дата без badge и без быстрого опроса успешного источника; доступные полные даты остаются |
| 200 alreadyExpired, в том числе пригодный декодируемый день | Нет badge; ровно +60 с при jitter=0, затем backoff; полчаса принудительного ожидания сняты, freshness не продлена |
| 200 max-age против Expires; Date/Age; дубликаты и неверные поля | Приоритеты и остаток срока по fixtures; max-age=0 не превращается в 1800; конфликт → conservative unknown |
| Короткий TTL 20 с, сосед свеж 2 ч | Первый скрывается на +20; повтор не раньше +60 и server gate; второй остаётся; бюджет останавливает частые обращения |
| 304 с частичными заголовками и matching validator | Сохранение отсутствующих полей; свежесть пересчитана; nil Expires не запускает TTL заново |
| 304 без тела, другой validator/variant/range | Нет reuse чужих данных; один unconditional GET на разрешённом слоте, без цикла |
| 429/503 Retry-After 120, дата, очень далёкая дата | Ни одного раннего запроса; delta не сокращается переводом часов; долгий срок не обрезается cap; нет быстрой серии |
| Retry-After отрицательный/дробный/NaN/overflow/прошедший; HTTP-date форматы | Без crash/мгновенного цикла; обычная ограниченная политика, корректные форматы распознаны |
| Offline, recovery, дребезг path, VPN с satisfied path и timeout | Offline без GET; один debounced recovery; серверные сроки сохранены; satisfied не считается успехом |
| Low Power, expensive/constrained, возврат в обычный режим | Быстрых серий нет; действующий cooldown и использованный бюджет не сброшены |
| Часы ±2 ч, sleep/wake, несколько пропущенных сроков | Нет burst/catch-up; монотонный backoff сохранён, спорная свежесть скрыта, один refresh |
| Midnight, 23/25-часовой DST, смена зоны | Новый query и реальные периоды; нет переноса fixed-24h максимума на другой день |
| Смена города/AUTO при сети, compute, retry, чтении/записи диска | Старые callbacks не меняют текущий контекст; provider Retry-After не обходится сменой города |
| OFF/delete last/cancel/shutdown; delete subset/shared date | Для последнего спроса всё отменено; subset сохраняет полезную сеть; поздний результат не возвращает badge или удалённый файл |
| Relaunch со свежим/истёкшим/повреждённым/слишком большим кэшем | Только свежий совпадающий пакет; нет TTL reset; ошибка файла не влияет на events и сетевой fallback |
| Schema mismatch, clock rollback, сетевой ответ обгоняет disk read | Старый формат/сомнительный срок не публикуется; свежая сеть не заменяется старым диском |
| no-store/no-cache/must-revalidate | Запреты reuse и записи соблюдены, stale не появляется |
| Медленное I/O, логгер под давлением, отмена вычисления | UI progress marker выполняется до завершения I/O; нет sync drain; bounded logs без приватных sentinels |

Для каждого случая проверять badge, количество стартов, точный deadline с заданным
jitter, отсутствие дубликатов scheduler и возможность отмены. Добавить sequence-тест
реального эпизода с synthetic MET alreadyExpired и двумя timeout, не утверждая, что
fixture воспроизводит неизвестные исходные заголовки.

## Этапы и критерии готовности

1. **Наблюдаемость без изменения контракта.** Добавить безопасные HTTP-метаданные в
   диагностику и deterministic fixtures для спорных заголовков, сохранить нынешние
   интервалы. Это отделит причину следующего эпизода от предположений.
2. **HTTP и повторы после решения владельца.** Добавить pure policy, ограниченную
   быструю серию, отдельные server deadlines и работу с монотонным временем.
   Сначала проверить контроллер на синтетике, затем recovery/wake мост. Обновить
   PRODUCT/ARCHITECTURE/VERIFICATION только под фактически реализованную семантику.
3. **Диск отдельным изменением.** Начать с ручных городов и только свежих данных,
   после одобрения хранения; AUTO оставить в памяти. Никакого stale по умолчанию.

Для реализации: полный SwiftLint и `./verify.sh fast`, затем применить product-qa
и `./verify.sh weather` для затронутой публикации/настроек; проверить UI progress
при искусственно медленной сети/диске. Real service и нативные location/wake сценарии
дают отдельное evidence только после реального выполнения. XCUITest нужен лишь при
добавленном внешнем UI-взаимодействии. Если изменение оформляется как user-visible
fix/release, освежить README captures по AGENTS из изолированных демонстрационных
данных, с provenance; снимки не доказывают восстановление сети.

Первоначальный разбор был только документацией и не выполнял матрицу реализации.
После отдельного согласования этапов 1–2 добавлены HTTP metadata, pure request policy
и lifecycle-bound монитор сети; состояние и scheduler остались у WeatherController.
Детерминированные проверки и нативная приёмка фиксируются отдельно с хешами рабочего
дерева; старые live HTTP/GUI результаты не считаются доказательством новой политики.
Диск и его строки в матрице выше остаются предложением, а не выполненной функцией.
Снимки пустого экрана — отдельный frozen этап с прежним executable provenance;
этот этап не перезаписывает их и не переименовывает в погодные доказательства.

## Альтернативы и решения владельца

### Фактическая приёмка этапов 1–2

Полный оптимизированный `./verify.sh fast` и SwiftLint пройдены на зафиксированных
исходниках. Матрица без диска покрыта HTTP fixtures, отдельными wall/monotonic clocks,
фиксированным jitter, barriers сетевых исходов/вычислений и наблюдаемыми snapshot.
Проверяется в том числе отсутствие запроса на +301 после постоянного invalid_response
и ровно следующий запрос на +1801; timeout имеет отдельную 10/45/300/900/1800-серию.
Тайм-ауты barriers остаются failure deadlines, а не способом задавать порядок событий.

Нативный `./verify.sh weather` на текущем хосте остановился после двух сценариев:
существующий драйвер не получил пункты SwiftUI city menu после pre-tracking update
(`[]`, AppKitPopUpAdaptor coordinator). Его проверка не ослаблена и не объявляется
пройденной. Выбор города и последующая публикация badges в этом запуске не подтверждены.
Принятый пустой экран проверяется отдельно интеграционным native smoke; его старые
восемь снимков и executable provenance не переписываются погодным этапом.

Реальные сервисы, VPN, AUTO/TCC, sleep/wake и смена Low Power/NWPath на устройстве
не тестировались и не выводятся из synthetic PASS. Поведение ContinuousClock и
waitsForConnectivity проверено по документации Apple; signal NWPath не принимается
за успешный HTTPS. Дисковые строки исходной матрицы и relaunch из кэша не реализованы.
Снимки интерфейса не обновляются погодным этапом: UI controls/copy/layout не изменены;
исторические release captures и отдельные unreleased empty-state captures сохранены.

Сократить глобальный timeout — недостаточно: медленная сеть станет чаще ошибаться,
а обязательное ожидание останется. Сократить все интервалы до минуты — лишний трафик,
нет защиты от 429 и принципиально неполных дней. Просто назначить receipt+1800 после
любого 200/304 — маскировка старого прогноза. URLCache вместо нормализованного кэша —
второй неявный слой состояния и риска приватности. Новые платные API и сервер сейчас
не устраняют дефект сроков и не входят в предложение.

Без смены продуктовой семантики можно улучшить диагностические данные и построить
регрессионные fixtures, сохраняя текущие сроки. Для остальных изменений нужны два
содержательных решения, а не выбор классов или чисел владельцем:

1. **Утвердить более быстрое восстановление при сохранении свежести.** Рекомендация:
   разрешить описанные bounded повторы и снять нынешние жёсткие 5/30-минутные
   нижние границы в соответствующих сценариях. UI и обещание полного дня сохранить.
2. **Разрешить ли прогноз на диске между запусками.** Рекомендация: отдельный этап,
   сначала только ручные города, свежие данные, очистка при OFF; AUTO пока не сохранять.
   Если нужен и AUTO, явно разрешить локальное хранение области и изменить privacy текст.

Отдельное решение о stale сейчас не требуется: рекомендовано его не вводить.
Ни один вариант не гарантирует получение погоды при блокировке сервисов или VPN.
